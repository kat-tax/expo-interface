# Windows

The kit runs on Windows through [react-native-windows](https://microsoft.github.io/react-native-windows/)
(New Architecture), and every control that has a Windows control draws it:
WinUI 3 XAML controls, hosted in XAML islands inside Fabric component views,
themed by Fluent and branded with the kit's accent. The pieces:

- **`index.windows.tsx` per component** — the Windows implementation, resolved
  by Metro for the `windows` platform like the `.ios`, `.android` and `.web`
  files are for theirs. None of them imports `@expo/ui`, which has no Windows
  implementation.
- **`windows/ExpoInterface`** — a C++/WinRT library of Fabric native
  components, one per WinUI control the kit hosts (`ExpoInterfaceButton`,
  `ExpoInterfaceToggleSwitch`, ...). Their JavaScript specs live in
  `src/windows/specs` and are compiled by React Native's codegen when the app
  builds. The library is autolinked into an app that depends on
  `expo-interface`.
- **Fluent tokens** — `theme.*` resolves to Fluent theme resources
  (`PlatformColor('TextFillColorPrimary')`), `fonts` to Segoe UI Variable,
  `variants` to the Fluent type ramp, and icons to Segoe Fluent Icons.

## Versions

Expo pins React Native; react-native-windows ships per React Native minor.
Pick the pairing that exists:

| Expo SDK | React Native | react-native-windows |
| --- | --- | --- |
| 54 | 0.81 | 0.81 — the pairing [expo-desktop](https://github.com/shirakaba/expo-desktop) ships templates for |
| 55 | 0.83 | 0.83 |
| 56 | 0.85 | 0.85 (preview at the time of writing) |
| 57 | 0.86 | not yet released |

The kit's peer range is Expo 57, whose React Native has no react-native-windows
release yet. The Windows platform files use react-native-windows 0.82's Fabric
API (the release that brought XAML islands to community modules), and the
native library was compiled and run in a react-native-windows 0.84 app
(React Native 0.84) while it was written: every island renders its WinUI
control in both themes, its events reach JavaScript, and its menus and
dropdowns open as windowed popups. A Windows build follows the next
react-native-windows release without changes to the kit; until then, a Windows
app of the kit is one on an earlier SDK whose react-native-windows exists.

## Setting up an app

Expo's own tooling has no `windows` platform: `expo prebuild` writes no
`windows/` folder and `expo run` has no Windows target. That is the job of
`expo-windows`, the runtime this repository is growing next to the kit — the
Metro config for the platform, an Expo Modules Core over react-native-windows,
the app scaffold (`init`, `run`, `bundle`) and the modules the Expo packages
call at load (`expo-linking`, `expo-constants`, `expo-asset`, `expo-font` and
the rest). The runtime exists — see [its README](https://github.com/kat-tax/expo-interface/tree/master/expo-windows#readme):
`withWindows(config)` in `metro.config.js` makes `expo start` serve a Windows
bundle, its install gives the Expo packages their modules, and its CLI
writes and runs the `windows/` project. Until react-native-windows pairs with
Expo 57 (see Versions) it is proven in the kit's harness, an Expo 57 app on
react-native-windows 0.84; the steps below are what that harness does, and
what `expo-windows init` automates.

1. Generate a react-native-windows `cpp-app` project into `windows/` on a
   React Native app of the matching version
   (`npx react-native-windows-init --template cpp-app`), and in its
   `.vcxproj` set `<WindowsPackageType>None</WindowsPackageType>` and
   `<WindowsAppSdkAutoInitialize>true</WindowsAppSdkAutoInitialize>`, so the
   unpackaged build bootstraps the Windows App Runtime (see Development).
2. Install the kit. It needs nothing else of its own: `react-native.config.js`
   in the package tells react-native-windows' autolinking where
   `windows/ExpoInterface` is, the codegen headers for its specs ship with
   the package, and the app's build compiles the library.
3. Give Metro the platform with `withWindows(getDefaultConfig(__dirname))`
   from `expo-windows/metro`: `resolver.platforms` gains `windows`,
   `react-native` resolves to `react-native-windows` for it (what
   react-native-windows' own `react-native start` does and `expo start` does
   not), the runtime's install runs before the entry, and `expo start` serves
   the bundle.
4. Keep what has no Windows implementation out of the Windows bundle. The
   kit's own files never import `@expo/ui`, `expo-image`, `expo-symbols`,
   `expo-web-browser` or `expo-system-ui` there (a test imports the whole
   package with them forbidden); an app's screens should not either, and the
   Expo packages that need a native module — Expo Router needs
   `expo-linking` — wait for the runtime.

[expo-desktop](https://github.com/shirakaba/expo-desktop) is the community
project that did all of this for Expo SDK 54 on react-native-windows 0.81 —
an Expo Modules Core, stubs, config plugins and a Metro config of its own. It
is the reference the runtime follows, not a dependency of the kit.

The machine needs what react-native-windows needs — Visual Studio 2022 with
the C++ desktop workload and the Windows 11 SDK, which
`rnw-dependencies.ps1` checks and installs:

```powershell
Set-ExecutionPolicy Unrestricted -Scope Process -Force
iex (New-Object System.Net.WebClient).DownloadString('https://aka.ms/rnw-vs2022-deps.ps1')
```

## Writing the app

Nothing changes in a screen: the same `Screen`, `FieldGroup`, `Switch` and
`Button` draw WinUI controls. Two things are Windows-aware at the app level.

### Navigation

`react-native-screens` draws nothing on Windows, so Expo Router's native stack
and native tabs cannot be used there. The kit exports a `Stack` that is Expo
Router's on iOS, Android and web and a stack of its own on Windows — Expo
Router's stack router under a drawn header, so `router.push`, `Link` and
`Stack.Screen` options all work — and its `Tabs` draws a WinUI
`NavigationView`: a row of items along the top of the window, or with
`windowsPane` the navigation pane down the left side — `left` expanded,
`compact` at its glyph-only width, the pane's toggle button switching between
the two, or `auto` deciding by the window's width at WinUI's own breakpoints
(the expanded pane from 1008 points, the compact one from 641, the top bar
below that). A route's `badge` is drawn in an `InfoBadge` on its item — a
count, or a dot for other text — and `windowsPlacement` puts it at the
pane's foot (`footer`, the bar's far end in the top mode) or makes it WinUI's
own settings item (`settings`, with its gear and its name), where a Windows
user looks for a settings screen. Use the kit's `Stack` in the root layout:

```tsx
// app/_layout.tsx
import {ThemeProvider} from 'expo-router';
import {AccentProvider, Stack, useNavTheme} from 'expo-interface';

function Navigation() {
  return (
    <ThemeProvider value={useNavTheme()}>
      <Stack screenOptions={{headerShown: false}}/>
    </ThemeProvider>
  );
}

export default function Layout() {
  return (
    <AccentProvider seed="#8959EA">
      <Navigation/>
    </AccentProvider>
  );
}
```

`TabStack` is that stack with the tab's root screen titled, as on the other
platforms. A modal route — `presentation: 'modal'` in its options — opens as
a card over smoke above the screen it came from, the way a WinUI dialog is
arranged, with its title and a back button in the card; Escape and a press on
the smoke close it. React Native's `Modal` is not involved (it cannot hold an
island on react-native-windows 0.84): the stack is a layer host, and a `Sheet`
anywhere below it draws in the same way.

`ExternalLink` opens its href in the default browser through React Native's
`Linking`, which react-native-windows implements. There is no in-app browser
to present, and `expo-web-browser`, which opens one on iOS and Android, has
no Windows module — importing it throws — so the kit's Windows files never
reach for it.

### Icons

Windows draws Segoe Fluent Icons. A token whose Material name has a Fluent
twin draws it without any change — `share` is `E72D`, `settings` is `E713`,
`star` is `E734` (and `E735` filled). `SEGOE_GLYPHS` is that table:
generated by `scripts/segoe-glyphs.ts` from the Material Symbols names
`expo-symbols` types and the Segoe Fluent Icons catalogue, a twin where the
names match (`zoom_in` is `ZoomIn`) and a curated list where they do not
(`arrow_back` is `Back`, `favorite` is `Heart`), with the family's solid form
as the filled glyph wherever it has one. A name outside the table draws
nothing; add it to the script's `CURATED` map and regenerate, or have the
token name its own code point with `windows`:

```ts
export const drop = icon(
  {ios: 'shippingbox', android: 'inventory_2', web: 'inventory_2', windows: 'E7B8'},
  drawables.inventory_2,
);
```

A token with neither draws nothing on Windows, as a bare SF Symbol name draws
nothing on Android and web.

### Colors and the scheme

`useColor`, `usePalette` and `AccentProvider` work as everywhere; every XAML
island takes the accent seed and the scheme as props, so a seeded app is
branded in WinUI too — the accent button's fill, the switch's on track, the
slider's thumb, the check mark, the selection indicators. `setColorScheme`
forces a scheme in JavaScript (react-native-windows follows the OS on its
own), which the islands follow.

`theme.*` on Windows resolves to Fluent theme resources where one matches —
`label` is `TextFillColorPrimary`, `background` is
`SolidBackgroundFillColorBase`, `separator` is `ControlStrokeColorDefault` —
which react-native-windows resolves per scheme and in high contrast. Tokens
with no Fluent twin (`tint`, `destructive`, `switchOn`) keep the palette
literal; `useColor` answers the palette for all of them.

High contrast is followed on `expo-windows`: while the user has a high
contrast theme on, `useColor`, `usePalette` and the navigation theme answer
the theme's own colours — text and separators in its text colour, surfaces
in its window and control faces, the accent its highlight — and follow the
user turning it on or off, as the Fluent resources do on their own.
`useHighContrast()` reads the setting (`enabled`, the theme's `scheme` name,
its `colors`) for anything that draws outside the palette;
`highContrastPalette(colors)` is the mapping. A selected surface takes a
control face, not the highlight, since the highlight is for text drawn in
its highlight text: a selection shows through its outline, as the themes
mean it to. Without the runtime, and everywhere else, the setting is off.

## What each component draws

| Component | Windows |
| --- | --- |
| Button | WinUI `Button`: the accent style for `filled`, the standard one for `outlined`, transparent for `text`; Segoe glyphs |
| Switch | WinUI `ToggleSwitch` at the trailing edge of a drawn row |
| Checkbox | WinUI `CheckBox` at the trailing edge of a drawn row |
| Slider | WinUI `Slider` |
| Stepper | WinUI `NumberBox` with inline spin buttons (`formatValue` is not applied, as on iOS) |
| Picker | WinUI `ComboBox` |
| SegmentedControl | WinUI `SelectorBar` (one size and shape; `accentColor` colors the indicator) |
| DateTimePicker | WinUI `CalendarDatePicker` and `TimePicker`, one or both by `mode` |
| Progress, Spinner | WinUI `ProgressBar` / `ProgressRing` |
| TextField | WinUI `TextBox` / `PasswordBox`, borderless in a row; the `inline` variant is React Native's input. `autoCapitalize` has no Windows equivalent; Enter submits and keeps the focus |
| ColorPicker | A color well opening a `Flyout` with the WinUI `ColorPicker`; presets are drawn |
| Menu, HeaderMenu, ContextMenu, PopupMenu | WinUI `MenuFlyout` — below the trigger, at the pointer on a right click or long press, or at a point |
| Alert | a dialog in `ContentDialog`'s arrangement — smoke over the whole window, the card with the title, the message and the actions — drawn in a windowed `Popup`, since a `ContentDialog` can only cover its own island (the `sheet` form is a dialog too) |
| Popover | WinUI `Flyout` with the title, message and actions; a popover with `children` is drawn |
| Toast | WinUI `InfoBar` over the bottom of the screen |
| Tooltip | react-native-windows' own tooltip, on hover and focus |
| IconToggle | WinUI `ToggleButton` with a `FontIcon` |
| Avatar | WinUI `PersonPicture` |
| Tabs | WinUI `NavigationView` over the focused tab: the top bar, or with `windowsPane` the left pane (expanded, compact, or `auto` by window width), the pane's toggle button collapsing it to its glyphs; a route's `badge` in an `InfoBadge`, `windowsPlacement` for footer items and the settings item |
| Stack, TabStack | Expo Router's stack router under a drawn header (`title`, `headerTitle` as text or a node, `headerLeft`, `headerRight`, `headerBackVisible`, `headerShown`); a pushed screen arrives with WinUI's entrance — up from a little below, fading in — and a modal settles from a little larger as a `ContentDialog` does, or `animation: 'fade' | 'none'`. A screen with `presentation: 'modal'` (or `formSheet`, `containedModal`, `fullScreenModal`) is a card over smoke above the screen below, a `transparentModal` lies over the window as it is — Escape, the smoke and the back button dismiss it; Alt+Left, the keyboard's back key and the mouse's back button pop the stack. On `expo-windows` the window's title follows the focused screen ("Settings – My App"), from the innermost focused stack |
| ExternalLink | Expo Router's `Link`, opening the href in the default browser through React Native's `Linking`: there is no in-app browser, and `expo-web-browser` has no Windows module |
| Gauge | Bars drawn in React Native; rings are the WinUI `ProgressRing` |
| Fab | Drawn, as on iOS; with `items` a `MenuFlyout` |
| Collapsible | Drawn (a WinUI `Expander` could not hold React Native content) |
| Sheet | A layer drawn in React Native over the window — WinUI's smoke and a centred card, the content scrolling inside — covering the whole window under the kit's `Stack` (a layer host) and the nearest ancestor elsewhere. Islands inside it are fine; React Native's `Modal` is not used |
| FieldGroup, ListItem, Card, Surface, Toolbar, Divider, Typography | Drawn with Fluent metrics and the Segoe UI Variable ramp |
| ConstrainedStackHeader | Nothing to draw: no web bar |
| KeyboardBar | Drawn; rides up on the touch keyboard through React Native's keyboard events, which `expo-windows` raises from the window's input pane (see below) |

The drawn pressables — a list row, a card, the disclosure header, the
header's back button, the floating action button — behave as WinUI's own
controls do at a desk: the subtle fill (or a control's secondary fill) under
the pointer and the tertiary one while pressed, react-native-windows' focus
ring when tabbed to, Enter and Space to press. A `ContextMenu` opens on the
Menu key and Shift+F10 as well as a right click. The XAML islands have all of
that from WinUI itself.

The title bar is the app's on `expo-windows`: `useWindowChrome({extend: true})`
in the root layout extends the content into it — no system title, the caption
buttons drawn for the scheme over the app's own top row — and the root
`Stack`'s header becomes the region that drags the window, leaving the
caption buttons their room on its right; with that header hidden nothing
drags the window (the system's whole top band would otherwise take the
presses on a pane's toggle or a top tab bar under it). A Mica or acrylic backdrop behind
the content is not there yet: a Win32 window on the Windows App SDK's
composition islands has no backdrop target in this release.

Keyboard shortcuts are a system: a menu item's `shortcut` (`Ctrl+S`,
`Ctrl+Shift+N`, `F2`) is drawn beside its label as WinUI draws an accelerator
and bound wherever the focus is while the menu is mounted, and
`useKeyboardShortcut('Ctrl+K', handler)` binds one from any screen. The keys
reach the kit's `Stack` from the focused control; of two bindings to one
shortcut, the later mounted wins, so a screen's is in front of its layout's.
On the other platforms the hook binds nothing and the shortcut text is not
drawn.

The touch keyboard — on a tablet, or a touch screen without a keyboard
attached — reaches React Native's `Keyboard` on `expo-windows`: the runtime
raises `keyboardDidShow` and `keyboardDidHide` from the window's input pane
with the rectangle it covers, so `Keyboard.addListener` and everything on it
work as on Android, and the kit's `KeyboardBar` rides up to meet it — the
bar measures its own bottom edge in the window, and the keyboard reports
where its top is, so the two meet whatever the window's height has become
since (`useWindowDimensions` never updates on a resize here) — and reports
its height through `onKeyboard`, with no library to install.
`ExpoWindows.showTouchKeyboardAsync()` and `hideTouchKeyboardAsync()` ask for
it, on the system's terms: it shows only while a text control has focus, and
a keyboard the user brought up from the taskbar stays. Without the runtime no
event fires and the bar stays put.

## How a control is hosted

Each native component is a Fabric component view whose content is a
`Microsoft.UI.Xaml.XamlIsland`. The island holds a `YogaXamlPanel` — a panel
that measures its control unconstrained and reports the size it wants to the
component's state — and the component registers a measure handler that hands
that size to Yoga, so a button hugs its content like a native button unless a
style stretches it. Props reach the control in `UpdateProps`; events go back
through the codegen'd emitter. `XamlHost.h` holds what every control shares:
the island, the measurement, the accent (the WinUI accent brushes overridden
in both theme dictionaries from the seed) and the theme.

Adding a control is a spec in `src/windows/specs`, a view in
`windows/ExpoInterface` and a line in the package provider; the specs are the
contract, and the tests assert on the props the islands receive. After a spec
change, `bun run codegen:windows` regenerates the headers in
`windows/ExpoInterface/codegen`, which are committed and shipped: an app
builds the library from `node_modules`, where react-native-windows' own
build-time `codegen-windows` has no React Native project to run in, so the
library turns that step off (`RunCodegenWindows`).

XAML is brought up before the first control is built: the island initializer
creates react-native-windows' `XamlApplication` (which initializes WinUI for
the thread and merges the control resources) unless the app already has an
application object. Islands follow the system theme like any WinUI control, so
the React Native tree behind them must paint the scheme's background — the
kit's `Screen` does — or dark controls sit on a white window. Menus, dropdowns
and the popover open as windowed popups, which is why they can extend past
their island; the alert's dialog is a windowed popup sized to the app window
for the same reason, since a `ContentDialog` can only cover the island it
lives in, and React Native's `Modal` cannot host an island on
react-native-windows 0.84.

## Development

The Vitest suite has a `windows` project: the iOS engine told it is Windows,
with `.windows.*` files resolved first and the modules that have no Windows
implementation forbidden — `@expo/ui`, `expo-image`, `expo-symbols`,
`expo-web-browser`, `expo-system-ui` and the rest of the list in
`vitest/setup.windows.ts` — so a `.windows` file that reaches for one fails
its test rather than the app. One test imports the whole barrel under that
rule, since that is what an app does. The islands render as host views named
after their native components, and the `*.windows.test.tsx` files assert on
their props and fire their events.

```sh
bun run test                       # ios, android, windows, web
bunx vitest run --project windows  # Windows alone
bun run codegen:windows            # regenerate the C++ headers from the specs
bun run segoe:windows              # regenerate SEGOE_GLYPHS from the icon catalogues
```

The native library builds inside a react-native-windows app — the app's
`run-windows` builds it, or MSBuild on the app's solution does. It has no
build of its own outside one, since it compiles against the app's
`node_modules/react-native-windows`.

To start the built `.exe` directly rather than through `run-windows` (which
registers the app with package identity), the app must bootstrap the Windows
App Runtime itself: the `cpp-app` template turns the Windows App SDK's
auto-initializer off, so set both in the app project's `Globals`

```xml
<WindowsPackageType>None</WindowsPackageType>
<WindowsAppSdkAutoInitialize>true</WindowsAppSdkAutoInitialize>
```

and have the Windows App Runtime of the SDK's version installed (its
`Microsoft.WindowsAppSDK.Runtime` package carries the MSIX files under
`tools/MSIX`). Without the bootstrap the app aborts on start with
`Microsoft.UI.Dispatching.DispatcherQueueController` not registered.
