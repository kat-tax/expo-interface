# Windows

The kit runs on Windows through [react-native-windows](https://microsoft.github.io/react-native-windows/)
(New Architecture). Every component that has a WinUI 3 control draws it,
hosted in a XAML island inside a Fabric component view, themed by Fluent and
branded with the kit's accent. What has no WinUI control is drawn with Fluent
metrics in Segoe UI Variable, and icons are Segoe Fluent Icons.

The pieces:

- **`index.windows.tsx` per component**, resolved by Metro for the `windows`
  platform like the `.ios`, `.android` and `.web` files are for theirs. None
  of them imports `@expo/ui`, which has no Windows implementation.
- **`windows/ExpoInterface`**, a C++/WinRT library of Fabric native
  components, one per WinUI control the kit hosts. Their specs live in
  `src/windows/specs`, and the library is autolinked into an app that depends
  on `expo-interface`.
- **Fluent tokens**: `theme.*` resolves to Fluent theme resources, `fonts` to
  Segoe UI Variable, `variants` to the Fluent type ramp.

The [expo-interface document](https://github.com/kat-tax/expo-interface/blob/master/docs/expo-interface.md#windows)
has the table of what each component draws on Windows and the differences
from the other platforms.

## Setting up an app

Expo's own tooling has no `windows` platform. `expo-windows`, the runtime in
the same repository, gives an app one: the Metro config, the Expo SDK's
modules on Windows, and the CLI that writes, builds and packages the
`windows/` project.

```sh
npx expo install expo-windows react-native-windows
```

```js
// metro.config.js
const {getDefaultConfig} = require('expo/metro-config');
const {withWindows} = require('expo-windows/metro');

module.exports = withWindows(getDefaultConfig(__dirname));
```

```sh
npx expo-windows init   # writes windows/ and patches it to run as an Expo app
npx expo-windows run    # expo start, then builds and launches the app
```

Install the react-native-windows that matches the app's React Native. Expo
SDK 57 pins React Native 0.86, which has no react-native-windows release yet;
the kit and the runtime are built and tested on the 0.84 line with Expo 57's
JavaScript, and an app follows the matching release when it ships. The
[expo-windows document](https://github.com/kat-tax/expo-windows/blob/master/docs/expo-windows.md)
has the setup in full, what every Expo package does on Windows, release
builds and packaging.

## Writing the app

Nothing changes in a screen: the same `Screen`, `FieldGroup`, `Switch` and
`Button` draw WinUI controls. Two things are Windows-aware at the app level.

### Navigation

`react-native-screens` draws nothing on Windows, so Expo Router's native
stack and native tabs cannot be used there. The kit's `Stack` is Expo
Router's on iOS, Android and web and a stack of its own on Windows, under a
drawn header, so `router.push`, `Link` and `Stack.Screen` options work the
same. Use it in the root layout:

```tsx
// app/_layout.tsx
import {ThemeProvider} from 'expo-router';
import {AccentProvider, Stack, useNavTheme} from 'expo-interface';

function Navigation() {
  return (
    <ThemeProvider value={useNavTheme()}>
      <Stack screenOptions={{headerShown: false}}/>
    </ThemeProvider>
  );
}

export default function Layout() {
  return (
    <AccentProvider seed="#8959EA">
      <Navigation/>
    </AccentProvider>
  );
}
```

`Tabs` draws a WinUI `NavigationView`: the top bar, or with `windowsPane` the
navigation pane down the left side (`left` expanded, `compact` at its
glyph-only width, or `auto` by the window's width at WinUI's own
breakpoints). A route's `badge` is drawn in an `InfoBadge`, and
`windowsPlacement` puts a route at the pane's foot or makes it WinUI's own
settings item.

A modal route (`presentation: 'modal'`) opens as a card over smoke above the
screen it came from, the way a WinUI dialog is arranged; Escape and a press on
the smoke close it. Alt+Left, the keyboard's back key and the mouse's back
button pop the stack.

### The window

With `expo-windows`, `useWindowChrome({extend: true})` in the root layout
puts the content in the title bar, with the root stack's header as the drag
region, and the window's title follows the focused screen. While the user has
a high contrast theme on, the palette answers the theme's own colors, and
`useHighContrast()` reads the setting for anything drawn outside the palette.
The touch keyboard reaches React Native's `Keyboard`, and `KeyboardBar` rides
up to meet it.

Keyboard shortcuts are a system: a menu item's `shortcut` (`Ctrl+S`, `F2`) is
drawn beside its label and bound while the menu is mounted, and
`useKeyboardShortcut('Ctrl+K', handler)` binds one from any screen.

## Icons

Windows draws Segoe Fluent Icons. A token whose Material name has a Fluent
twin draws it without any change: `share` is `E72D`, `settings` is `E713`,
`star` is `E734` and `E735` filled. `SEGOE_GLYPHS` is that table, generated by
`scripts/segoe-glyphs.ts` from the Material Symbols names and the Segoe
Fluent Icons catalogue: a twin where the names match, a variant taking its
base's glyph, and a curated list where the names differ. A name outside the
table draws nothing; the Windows test names the glyphs to choose from, and
adding the name to the script's `CURATED` map and running
`bun run segoe:windows` fixes it. A token can also name its own code point:

```ts
export const drop = icon(
  {ios: 'shippingbox', android: 'inventory_2', web: 'inventory_2', windows: 'E7B8'},
  drawables.inventory_2,
);
```

## Colors

`useColor`, `usePalette` and `AccentProvider` work as everywhere; every XAML
island takes the accent seed and the scheme as props, so a seeded app is
branded in WinUI too. `setColorScheme` forces a scheme in JavaScript, which
the islands follow. `theme.*` resolves to Fluent theme resources where one
matches (`label` is `TextFillColorPrimary`, `background` is
`SolidBackgroundFillColorBase`, `separator` is `ControlStrokeColorDefault`),
which react-native-windows resolves per scheme and in high contrast; tokens
with no Fluent twin (`tint`, `destructive`, `switchOn`) keep the palette
literal.

## Development

The Vitest suite has a `windows` project: the iOS engine told it is Windows,
with `.windows.*` files resolved first and the modules that have no Windows
implementation forbidden, so a `.windows` file that reaches for one fails its
test rather than the app. The islands render as host views named after their
native components, and the `*.windows.test.tsx` files assert on their props
and fire their events.

```sh
bun run test                       # ios, android, windows, web
bunx vitest run --project windows  # Windows alone
bun run codegen:windows            # regenerate the C++ headers from the specs
bun run segoe:windows              # regenerate SEGOE_GLYPHS from the icon catalogues
```

The native library builds inside a react-native-windows app; it has no build
of its own outside one. `scripts/windows-ci.sh <workdir>` is that build end
to end, which the Windows workflow runs on every change to the kit, the
runtime or the example. The harness drives a built app:

```sh
bun run harness -p windows --target <path to the exe> open /detail screenshot detail.png tree
```
